## Build, in three waves (each ends green, backend closed)

### Wave 1: backend
These follow D1 and D2.
- **`PpFoodTriesStore`**: a singleton `ChangeNotifier`, per child. Each row holds an app-generated id, `child_id`, `food`, `first_tried` (a date) and an optional `reaction` (none / mild / see doctor, plus a note). It is local-first, and sync goes through `supabase_repo.dart` the way milestone observations do: per-child records, shared with the co-parent.
- Migration 0115 `pp_food_tries` (RLS: the child's family) and a contract test that pins the columns.
- **Consent kind `foods`** ("Foods tried": why "so Recipes and Before you see the doctor can use it"). The ask card appears after the first "Tried it". Readers check `allows(foods)`.
- Allergy reads (D2) use `HealthStore.knownAllergies` for the active child. No new storage.
- Docs: sync log step 20, STILL-OPEN-BACKEND row 20, a BACKEND-PATTERNS entry on choosing a child record over a personal one (who needs to see it decides the table), and the migration in BEFORE-LAUNCH / the run list.

  - the store round-trips
  - logging out keeps the local rows, and an uninitialised backend behaves like logged out
  - the contract columns
